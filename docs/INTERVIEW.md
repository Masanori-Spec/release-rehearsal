# 面接で説明するための論点

この文書は説明の練習用です。本人が担当・理解したと確認できない作業を、自分だけの実績として話すための台本ではありません。

## 30秒の概要

「Vite の古いタブが、更新後に存在しない lazy chunk を参照する問題を題材にしました。2つの manifest と保持方針から、不足するファイルへの依存経路を説明します。実行時の通信は推定せず、同名ファイルも hash がなければ内容不明にしています。小さな実 Vite ビルドと、独立したグラフ oracle でモデルを検証する構成です」

## 深掘りされる判断

- なぜ単なる diff ではないか: 選択 entry からの到達性、非連結な変更、共有依存、CSS・asset の連鎖を扱う
- なぜ安全/危険の二値にしないか: 読込済みの entry JS、cache、Service Worker、API、CDN を manifest は記述しない
- なぜ同一パスを別分類にするか: パス一致・bytes一致は内容一致の証明にならない。新側優先の衝突を保持だけでは解決できない
- なぜ Worker か: 悪意や巨大入力への上限だけでなく、中断・再入力・古い解析結果の表示防止を必要とした
- なぜ固定 fixture と独立 oracle の両方か: 同じ算法を繰り返すテストでは共通の誤りを見逃す。公式ビルドとの対応と集合計算の正しさは別の主張
- なぜ負の対照か: unrelated 更新は旧 entry URL を変えても、既に開いたタブの unchanged lazy branch は成功し得る。graph loss と runtime failure の混同を検出する

## 自分で再現する課題

1. npm test と fixture:verify を実行し、実 manifest の lazy.js → shared / css / svg を説明する
2. 同一パス・異なる SHA-256 の inventory を作り、retain-all が衝突を直さない理由を説明する
3. 動的参照に cycle を追加し、終了性と最短 witness の不変条件を説明する
4. ファイル読込中の再計算を再現し、epoch と sequence の役割の違いを説明する
5. CI が失敗した場合に、未実施・失敗・成功を区別して検証記録を更新する

## 現時点で主張しないこと

実顧客の導入、障害削減率、需要実証、独自発明、全 Vite plugin / 全 path 互換、実 deployment の安全性。ブラウザ gate の結果は必ず最新の検証記録に合わせる。
